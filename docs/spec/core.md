# squiz 핵심 규약

이 문서는 상태 기계가 강제하는 런타임 계약을 정의합니다. 인식론적 불변조건, 응답 승인 규칙, AI와 사용자 사이의 통신, 저장 구조, 구현 스택입니다.

**먼저 읽을 것:** [설계 명세](design.md). 이 문서는 그 명세에서 정의한 용어(claim, evidence, 에피소드, scaffold, taint, restore 등)를 그대로 씁니다.

## 1. 인식론적 불변조건

여덟 가지이며 전부 CLI(상태 기계)가 강제합니다. 위반하는 이벤트는 거부됩니다.

[설계 명세](design.md) §15의 교수법 불변조건 P1~P8이 **무엇을 가르치는가**에 대한 규칙이라면, 여기 I1~I8은 **무엇을 사실로 취급하는가**에 대한 규칙입니다.

| # | 불변조건 | 강제 지점 |
|---|---|---|
| I1 | **검증되지 않은 반례로 모순을 대면하지 않는다.** consequence 질문과 재확인 피드백은 verify 상태가 `supported`인 evidence를 참조해야 한다 | `ask --kind consequence`가 evidence 참조의 verify 상태를 검사 |
| I2 | **오염 복구가 최우선이다.** 복구 대기열이 비어 있지 않으면 허용 동작은 `restore`뿐이다 | 허용 동작 계산 |
| I3 | **모든 응답은 등록된 질문에 귀속된다.** 응답의 질문 식별자가 현재 대기 중인 질문과 일치해야 승인된다 | 응답 수신 시 식별자 검사 |
| I4 | **한 질문에 한 응답.** 승인된 응답은 수정할 수 없고 중복될 수 없다. 정정은 새 질문으로만 가능하다 | 응답 파일의 원자적 교체 + 식별자 소진 |
| I5 | **판정은 현재 버전을 참조한다.** 판정은 그 시점의 claim 버전과 evidence 버전을 함께 기록하며, 참조한 버전이 철회되면 그 판정은 오염된다 | 판정 이벤트에 버전 기록, 철회 시 의존 판정 무효화 |
| I6 | **확신을 동반한 반대는 원천 재확인을 강제한다.** 사용자가 `sure`로 claim과 반대되는 답을 하면 원천(실행 결과 또는 외부 근거)을 다시 본다. 완료 전까지 consequence는 잠긴다 | 판정 결과가 `contradicted`+`sure`이면 허용 동작을 재확인 계열로 제한 |
| I7 | **무효한 질문의 답은 판정하지 않는다.** `question_quality`가 `valid`가 아니면 판정 필드는 기록만 되고 단계·에피소드 갱신에 쓰이지 않는다. 판정 문항에 세지 않고 부담 문항에는 센다 | 판정 처리 분기 |
| I8 | **허용된 동작만 수행한다.** 모든 명령은 현재 상태의 허용 집합 검사를 통과해야 한다. TUI의 구조적 선택도 응답으로서 승인 절차를 거친다 | 상태 기계 진입점 |

## 2. 응답 승인

1. `ask`가 질문을 등록하고 질문 식별자를 발급합니다. **대기 중인 질문은 항상 최대 1개**입니다(한 화면 한 질문).
2. TUI는 대기 중인 질문만 표시합니다. 사용자의 응답(텍스트 + 확신도, 또는 구조적 선택)은 질문 식별자를 포함해 원자적으로 기록됩니다.
3. waiter(`squiz wait`)는 응답이 승인되면 해당 exit 코드로 종료합니다. 승인된 응답은 수정할 수 없고(I4), 정정은 다음 질문이나 이의 제기(exit 7)로 합니다.
4. 힌트 등급 선택, "작은 단서 / 예시 / 설명" 선택, "계속 / 요약 종료 / 설명 전환" 선택은 모두 **구조적 응답**이며 텍스트 답변과 동일한 승인 절차를 거칩니다.
5. 질문이 대기 중인 동안 새 `ask`는 거부됩니다. 질문 폐기와 되묻기 절차만 예외입니다.

## 3. waiter exit 코드

`squiz wait`는 블로킹 명령이며, **exit 코드가 곧 사용자가 무엇을 했는지를 알려주는 통신 채널**입니다. AI는 이 코드로 다음 행동을 정합니다.

| exit | 뜻 | AI의 다음 행동 |
|---|---|---|
| 0 | 답변 승인됨. stdout에 응답 JSON | 판정(`judge`) |
| 2 | 되묻기 — "질문이 무슨 뜻인가요?" | `clarify_reply` (2회째는 양식 전환, 3회째는 질문 폐기) |
| 3 | 타임아웃 (응답 없음). 질문은 대기 상태 유지 | 계속 대기하거나 사용자에게 확인 |
| 4 | 세션 중단 요청 | 종결 (`end_reason=aborted`) |
| 5 | 내부 오류 (세션 상태 손상 또는 통신 실패) | 진행 중단, 사용자에게 보고 |
| 6 | 설명 요청 | `explanation record` |
| 7 | 이의 제기 | `objection --discard` 또는 `--investigate` |
| 8 | 건너뛰기 | 개념 `deferred` |

exit 0이 아닌 경우에도 stdout에 부가 정보 JSON(선택 이유 등)이 출력될 수 있습니다.

## 4. 저장 구조

파일이 원천입니다. 서버 프로세스는 없습니다.

```
.squiz/
  session.json            # 활성 세션 포인터 {id}
  sessions/<id>/
    events.jsonl          # append-only 이벤트 로그 (원천)
    state.json            # 최신 스냅샷 (이벤트 재생으로 항상 재구성 가능)
    q/                    # AI와 TUI 사이의 질문·응답 교환
      question.json       # 현재 대기 중인 질문 (원자적 교체로 게시)
      response.json       # TUI가 원자적 교체로 게시, CLI가 승인 후 소비
```

규칙:

- 모든 쓰기는 임시 파일에 쓴 뒤 `rename`으로 교체합니다. 읽는 쪽은 부분적으로 쓰인 파일을 보지 않습니다.
- **`state.json`은 캐시입니다.** 로그와 어긋나면 `events.jsonl` 재생이 이깁니다.
- 이벤트는 `{seq, ts, type, payload}` 형태입니다. `seq`는 단조 증가하며, 재생 시 순서대로 상태 변환을 적용합니다.
- 같은 이벤트 로그를 재생하면 항상 같은 상태가 나와야 합니다. 이 결정성은 테스트로 검증합니다.

## 5. 프로세스 간 통신

세 프로세스가 위 `q/` 디렉터리를 통해 통신합니다.

- **AI 쪽** — `squiz ask`가 `question.json`을 게시하고, `squiz wait`가 `response.json`을 폴링합니다.
- **사용자 쪽** — `squiz ui`가 `question.json`을 폴링해 표시하고, 답이 입력되면 `response.json`을 게시합니다.
- **승인** — CLI가 응답의 질문 식별자를 검사해 승인한 뒤에만 소비합니다(I3, I4).

HTTP 서버를 두지 않은 이유는 "파일이 원천"이라는 원칙과 일치시키기 위해서입니다. waiter와 TUI가 독립 프로세스로 동작하고, 어느 쪽이 죽어도 상태는 디스크에 남습니다.

## 6. 구현 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어 | Go (모듈 `github.com/agentwiki/squiz`) | 단일 바이너리 배포, TUI 생태계 |
| TUI | bubbletea + lipgloss | Go TUI 표준 |
| 통신 | 파일 기반 (§5) | "파일이 원천" 원칙과 일치, 서버 불필요 |
| CLI 구조 | 표준 라이브러리 서브커맨드 | 상태 기계가 본체이고 플래그 파싱은 단순 |
| 배포 | GitHub Releases + goreleaser, `go install github.com/agentwiki/squiz/cmd/squiz@latest` | Go 표준 배포 |

## 7. 패키지 구조

| 경로 | 역할 |
|---|---|
| `cmd/squiz` | 진입점 |
| `internal/engine` | 상태 기계. 문서가 "CLI가 강제한다"고 적은 모든 규칙이 여기 있다 |
| `internal/cli` | 서브커맨드 껍데기. stdout은 JSON, 오류는 stderr |
| `internal/store` | 이벤트 로그와 스냅샷 (§4) |
| `internal/ipc` | 질문·응답 파일 교환 (§5) |
| `internal/tui` | 사용자 화면 |
| `e2e` | 모의 AI 튜터와 모의 사용자가 실제 바이너리를 구동하는 시나리오 테스트 |

`internal/cli`와 `internal/tui`는 얇은 껍데기입니다. 규칙을 추가하거나 고칠 때는 `internal/engine`을 고치고, [상태 전이표](transitions.md)를 함께 갱신하세요. 생성형 테스트가 그 표를 기준으로 삼습니다.
